KAMASH Eau de Parfum

Client project · Brand & storefront frontend

Kamash Fragrance

A luxury perfume brand needed a premium single-page presence — without the overhead of a full e-commerce backend. I designed and built the complete frontend solo: a shop-like experience with cart, wishlist and quick-view interactions, running as static files on GitHub Pages.

  • HTML5
  • CSS custom properties
  • Vanilla JS
  • Intersection Observer
  • GitHub Pages
Live site ↗ Source ↗
Case study

Problem

A small fragrance brand wanted a website that felt as considered as the product, on a zero-infrastructure budget: no server, no CMS, no licences.

Approach

  • Design system in CSS custom properties: charcoal, beige and metallic gold with a Playfair Display / Montserrat type pairing.
  • Client-side cart, quantity controls and wishlist state, so the static page behaves like a shop.
  • Intersection Observer scroll-reveal animations instead of scroll-event handlers — smooth at 60fps and cheap on battery.
  • Quick-view modals, toast alerts and an inquiry flow, all keyboard- and screen-reader-considered.

Result

A fast, fully responsive brand site deployed on GitHub Pages — the project that set the standard for everything else on this page.

Problem

Timer apps are a de facto React tutorial — I wanted to show the same product thinking in plain JavaScript, with none of the bundle cost.

Approach

Personal project · API integration demo

Skyline

A live weather dashboard that pulls real forecast data from the Open-Meteo API — with the unglamorous parts done properly: cancelled stale requests, retryable errors, loading skeletons and geolocation permission handled with grace.

  • Fetch + AbortController
  • Open-Meteo API
  • Hand-drawn SVG charts
  • Geolocation
  • Debounced search
Live site ↗ Source ↗
Case study

Problem

Most weather demos assume the API always succeeds. I wanted to showcase the failure paths a real product lives or dies by.

Approach

  • Debounced city search with an arrow-key-navigable suggestion list on top of Open-Meteo's free, key-less geocoding.
  • AbortController cancels in-flight requests when a newer search starts — no race conditions on screen.
  • The 24-hour temperature chart and all weather icons are hand-authored SVG; no charting library was harmed.
  • Loading skeletons, error states with retry, "city not found", denied-location — every branch has an honest UI.

Result

A dashboard where every number on screen came from a live API call, and every way it can break has a considered answer.

Personal project · React framework demo

Splitzy

A bill-splitting app built in React to show framework thinking, not just framework syntax: derived state through useMemo, a custom useLocalStorage hook, context instead of prop drilling — and a greedy "settle up" algorithm that suggests the fewest transfers to balance the group.

  • React 18
  • Hooks
  • Context API
  • useMemo
  • Custom hooks
Live demo ↗
Case study

Problem

My public work so far is framework-free. This project answers the obvious recruiter question — can the same developer work in React, idiomatically?

Approach

  • Component tree (PersonManager, ExpenseForm, BalancePanel, SettleSuggestions) with state kept as close to the data as possible.
  • Balances are never stored — they're derived with useMemo, so the UI can't drift from the data.
  • Custom useLocalStorage hook persists everything; Context replaces prop drilling two levels deep.
  • "Settle up" runs a greedy min-transfer algorithm over the balance map — the kind of small real algorithm frameworks don't give you.
  • Honest trade-off: this demo ships React via CDN with in-browser JSX compilation — zero build tooling, at the cost of a few hundred KB. A production build would pre-compile with Vite.

Result

A working product feature — split a dinner bill and see who owes whom, live.

Why I added React to a framework-free portfolio

Opinion, stated as such: this is one developer's judgment about one project, not advice.

This page used to carry a post titled "Why this portfolio has no framework." It's gone, and the reason is Splitzy. The old argument — ship no dependencies you didn't choose — was about a page that renders four paragraphs and a grid. It stopped being true the moment I built something with real state: expenses that mutate, per-person balances that recompute from that mutation, localStorage that survives reloads, and a settle-up list that has to stay consistent across all three.

In plain JS that becomes a hand-written event bus and a render function I would have to keep in sync by discipline. With React it is useState, a useLocalStorage hook, and derived values that cannot drift, because recomputing them is the model rather than something I remember to call. Two useContext layers replaced prop drilling through four components. That is the honest trade: the framework bought correctness I would otherwise have had to test for.

What it cost, also stated honestly: Splitzy loads React 18 from a CDN with Babel in the browser, so there is no build step, no bundler and no code splitting — fine for a demo, not what I'd ship to a client. The portfolio page itself still has no framework, because the reason it had none still holds. A tool earns its place per project, not per resume keyword.
